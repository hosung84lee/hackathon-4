# 신상품 보험 AI 워크플로우 프로토타입 — 전체 프로세스

## 1. 목표

- **자동화 범위**: 보험사에서 신상품이 출시될 때, 상품 정의부터 시스템 반영까지를 AI 워크플로우로 자동화한다.
- **AI 적용 영역**: 기존 업무 프로세스 중 AI가 잘할 수 있는 영역을 찾아 AI를 적용한다.
- **역할 전환**: AI 도입 후 담당자의 역할이 **업무 수행자**에서 **AI 수행 결과의 최종 검토·승인자**로 바뀌는 것을 보여준다.

---

## 2. 업무 흐름 개요

이번 프로토타입에서 보여줄 흐름은 2가지다.

| # | 흐름 | AI가 하는 일 | 사람이 하는 일 |
|---|------|------------|-----------|
| 1 | 보험약관(사고보장) 구조화 | 약관 분석 → 표준 스키마로 변환 → 보험금 계산 Tool 생성 | 스키마 미정의 항목 검토, 결과 승인 |
| 2 | 보험금 청구 심사 지원 | 서류 분류·청구정보 생성 → 판단 항목 심사 → 보험금 계산 | 판단 결과 최종 검토·승인 |

> 흐름 1에서 정의된 **AI 판단 항목**이 흐름 2의 심사에서 사용된다.

---

## 3. 흐름 1 — 보험약관(사고보장 부분) 구조화

### 3.1 개요

보험약관에서 사고보장 약관을 추출해, 사전에 정의된 **JSON 스키마**에 맞게 파싱한다.

### 3.2 기대 효과

- **현재 문제**: 1,000페이지가 넘는 약관을 사람이 해석하고, 기존 시스템과 달라진 부분을 찾아 시스템에 반영하기까지 시간이 오래 걸린다.
- **영향**: 이 리드타임이 길어질수록 시장 상황에 맞춰 상품을 빠르게 출시하기 어렵다.
- **목표**: AI로 **상품 출시 → 시스템 반영** 시간을 줄여 시장에 빠르게 대응한다.

### 3.3 워크플로우

| 단계 | 작업 | 수행 주체 | 비고 |
|----|------|---------|------|
| 1 | 보험약관 PDF 텍스트 추출 | 도구 | PyMuPDF 또는 약관분석 서비스 *(검토 중)* |
| 2 | 사고보장 관련 페이지 추출 | Agent | |
| 3 | PDF 재생성 | 도구 | 필요한 페이지만 |
| 4 | 표준 스키마 구조로 변환 | Agent | 입력: 추출 텍스트 + 재생성 PDF + 표준 스키마 |
| 5 | 보험금 계산 Tool 생성 | Agent | '보험금계산 프로그램 생성' Skill 사용 |
| 6 | 검토·승인 | 담당자 | 변환 결과, 스키마 미정의 항목, 계산 Tool을 한꺼번에 검토하고 승인 |
| 7 | 신상품 시스템 반영 | 프로그램 | 승인된 구조화 약관, 판단 항목, 계산 Tool을 저장해 흐름 2에서 쓸 수 있게 함 |

```
약관 PDF ─▶ 텍스트 추출 ─▶ 사고보장 페이지 추출(Agent) ─▶ PDF 재생성
        ─▶ 스키마 변환(Agent) ─▶ 보험금 계산 Tool 생성(Agent)
        ─▶ 담당자 검토·승인 ─▶ 시스템 반영
```

> 6단계에서 담당자는 직접 약관을 해석하는 대신 **AI 결과를 검토·승인**한다. 반려하면 시스템에 반영하지 않고 종료한다.

### 3.4 핵심 원칙 — 추측 금지, 에스컬레이션

> ⚠️ **4단계(스키마 변환)에서 가장 중요한 원칙**
>
> 약관에 표준 스키마에 정의되지 않은 항목이 있으면, Agent는 **추측하거나 임의로 만들어내지 않는다.**
> 대신 해당 항목을 비워두거나, "이런 항목이 스키마에 없으므로 추가 정의가 필요하다"고 **에스컬레이션**한다.

**에스컬레이션 방식 — 수집형**

- 미정의 항목을 만나도 **변환을 멈추지 않는다.** 해당 값은 비워두고 끝까지 변환한다.
- 변환 Agent의 출력 스키마에 **미정의 항목 목록** 필드를 둔다.

| 필드 | 설명 |
|-----|------|
| 항목명 | 약관에 있지만 스키마에 없는 항목 |
| 약관 위치 | 조항 번호, 페이지 |
| 사유 | 스키마에 없는 이유, 추가 정의가 필요한 내용 |

- 목록에 항목이 있으면 6단계 검토·승인 화면에서 강조해서 보여준다.
- 흐름 2의 판단 불가는 이와 달리 **종료형**(`escalate` 툴)으로 처리한다 (6.4, 6.5).

### 3.5 생성된 계산 Tool 취급

5단계에서 LLM이 만든 계산 Tool은 코드이므로 아래 규칙으로 다룬다.

| 항목 | 내용 |
|-----|------|
| 사람 승인 | 6단계 검토·승인을 통과한 Tool만 시스템에 반영한다 |
| 실행 방식 | 흐름 2는 계산 Tool을 **별도 프로세스로 실행**한다. 입력(청구정보 + 판단 결과)과 출력(계산 결과)은 JSON으로 주고받는다 |
| 시간 제한 | 별도 프로세스에 시간 제한을 걸어, 생성 코드가 멈추거나 오류가 나도 앱에 영향이 없게 한다 |
| git | 실행할 때마다 만들어지는 파일이므로 **커밋하지 않는다** |

## 4. 흐름 2 — 보험금 청구 심사 지원

### 4.1 개요

보험금 청구 심사에는 두 종류의 판단 조건이 있다.

| 구분 | 설명 | 처리 방식 (AS-IS → TO-BE) |
|-----|------|------------------------|
| 프로그램 체크 조건 | 청구서에 명확히 나와 있어 프로그램으로 체크할 수 있는 조건 | 프로그램 → 프로그램 (변경 없음) |
| 심사자 판단 조건 | 의사의 진단 내용을 바탕으로 사람이 판단해야 하는 조건 | 심사자 → **Agent 판단 + 심사자 검토·승인** |

두 번째 조건을 Agent에 위임한다. Agent는 다음 3가지를 출력하고, 심사자는 이를 최종 검토·승인한다.

1. **판단 결과**
2. **판단 근거**
3. **판단에 사용한 소스**

### 4.2 워크플로우

| 단계 | 작업 | 수행 주체 | 내용 |
|----|------|---------|------|
| 1 | 청구서류 업로드 | 고객/담당자 | |
| 2 | 이미지 분류 및 태깅 | Agent | 분류: 진단서 / 영수증 / 기타 진단서류<br>태깅: 각 이미지 내용을 1~2줄로 요약 |
| 3 | 청구정보 자동 생성 | Agent | 영수증·진단서·세부내역서에서 텍스트를 추출해 사전 정의된 JSON 구조로 생성 |
| 4 | 판단 필요 항목 식별 | 프로그램 | 상품의 판단 항목 정의(흐름 1 결과)와 청구정보를 비교해 AI가 판단할 항목을 찾음 |
| 5 | AI 판단 항목 처리 | Agent | 4단계에서 찾은 항목이 있으면 Agent에 위임 (없으면 건너뜀) |
| 6 | 보험금 계산 | 프로그램 | 청구정보 + AI 판단 결과로 계산 |
| 7 | 검토·승인 | 심사자 | 판단 결과와 계산된 보험금 최종 검토 |
| 8 | 보험금 지급 | — | |

```
서류 업로드 ─▶ 분류·태깅 ─▶ 청구정보 생성(JSON) ─▶ 판단 필요 항목 식별
          ─▶ [필요 시] Agent 판단 ─▶ 보험금 계산 ─▶ 심사자 검토·승인 ─▶ 지급
```

> AI 판단 결과(예: 소액암 여부)가 지급액을 바꾸므로, **판단을 먼저 하고 보험금 계산은 최종 입력값으로 한 번만** 한다.

### 4.3 AI 판단 프로세스

AI가 판단해야 하는 항목은 **흐름 1(약관 구조화) 과정에서 정의**된다.

#### 판단 항목 정의 구조

| 항목 | JSON 키 | 설명 |
|-----|---------|------|
| 판단코드 | `code` | 판단 항목의 고유 코드 |
| 판단코드명 | `name` | 판단 항목 이름 |
| 판단하는 방법 | `description` | 판단 기준, 필요한 서류, 판단 불가 조건 |
| 약관 관련 조항 | `clauseRef` | 근거가 되는 약관 조항 |
| 판단 결과 Output 정의 | `outputSchema` | Agent가 출력할 결과 구조 |

#### 예시 — 소액암 여부

```json
{
  "code": "MINOR_CANCER_YN",
  "name": "소액암여부",
  "description": "진단받은 암이 소액암인지 판단한다. 소액암 기준은 암의 크기가 1cm 미만이고 림프절 전이가 없어야 한다. 판독지 결과를 보고 판단하며, 해당 서류가 없으면 판단할 수 없다.",
  "clauseRef": "제2조 3항 …"
}
```

## 5. 개발 환경

| 구분 | 기술 |
|-----|------|
| 프로토타입 UI | Streamlit |
| Backend | Python |
| DB | SQLite |

### 폴더 구조

```
src/
├── app/          # Streamlit UI (main.py + views/)
├── backend/      # 설정, DB, 파일 저장
├── schema/       # Pydantic 모델
├── workflow/     # 처리 파이프라인
├── trace/        # trace 기록·조회 (Langfuse 방식)
├── agent/        # Agent loop, 툴콜링, 스킬 로더 (직접 구현, OpenAI API)
├── mcp_server/   # MCP 서버
├── skills/       # 에이전트용 스킬/도구
└── data/
    ├── pdf/
    ├── image/
    └── db/       # SQLite
```

### workflow 구성 규칙

- **플로우 1개 = 워크플로우 파일 1개**
- **플로우 안의 스텝은 스텝마다 별도 파일**로 만든다.
- 워크플로우 파일은 **스텝 실행 순서, 스텝 간 연결, 분기 조건**만 담당한다. 실제 처리 로직은 스텝 파일에 둔다.

```
src/workflow/
├── policy_structuring.py          # 흐름 1: 스텝 순서·분기만
├── claim_review.py                # 흐름 2: 스텝 순서·분기만
└── steps/
    ├── policy_structuring/
    └── claim_review/
```

### 스텝 작성 규칙

> 스텝은 Agent 실행만이 아니라 **워크플로우 안의 모든 작업 단위**를 뜻한다. 도구 실행(텍스트 추출 등), 프로그램 동작(보험금 계산, 시스템 반영 등), 사람의 검토·승인도 각각 하나의 스텝이다. 아래 규칙은 수행 주체(`actor`)와 상관없이 모든 스텝에 똑같이 적용한다.

| 규칙 | 내용 | 이유 |
|-----|------|------|
| 입출력 통일 | 모든 스텝은 공통 컨텍스트(ctx)를 받아 갱신된 컨텍스트를 돌려준다 | 스텝을 고치지 않고 흐름만 바꿀 수 있다 |
| 스텝 간 직접 호출 금지 | 스텝은 다른 스텝을 부르지 않는다 | 흐름은 워크플로우 파일 한 곳에서만 관리한다 |
| 분기는 워크플로우에서만 | 분기 조건 판단은 워크플로우 파일이 담당한다 | 흐름을 한눈에 파악하고 시각화하기 쉽다 |

### 워크플로우·스텝 어노테이션

워크플로우와 스텝은 **상하위 구조**다. 워크플로우에는 `@workflow`, 스텝에는 `@step` 어노테이션을 붙인다.

#### `@workflow` — 워크플로우 정보

| 항목 | 필수 | 설명 | 예시 |
|-----|-----|------|------|
| `code` | ✅ | 워크플로우 코드 (영문, 워크플로우 종류 구분) | `claim_review` |
| `name` | ✅ | 워크플로우명 | 보험금 청구 심사 지원 |

#### `@step` — 스텝 정보

| 항목 | 필수 | 설명 | 예시 |
|-----|-----|------|------|
| `id` | ✅ | 스텝 ID (워크플로우 안에서 유일) | `judge_items` |
| `name` | ✅ | 스텝명 | AI 판단 항목 처리 |
| `workflow` | ✅ | 상위 워크플로우 코드 | `claim_review` |
| `actor` | ✅ | 수행 주체 | `tool` / `agent` / `program` / `human` |

#### 워크플로우 ID — 실행 건마다 유일

워크플로우가 **실행될 때마다 고유한 워크플로우 ID를 발급**한다.

| 구분 | 내용 |
|-----|------|
| 형식 | `{워크플로우 코드}_{일련번호 6자리}` |
| 예시 | `claim_review_000001`, `claim_review_000002`, `policy_structuring_000001` |
| 일련번호 | 워크플로우 코드별로 1부터 증가 |
| 발급 | 워크플로우 실행 시작 시 SQLite에서 해당 코드의 마지막 번호 + 1로 발급 |
| 유일성 보장 | 워크플로우 ID 컬럼에 UNIQUE 제약, 발급과 저장을 한 트랜잭션에서 처리 |

- 코드가 ID 앞에 붙어 있어서 **ID만 보고도 어떤 워크플로우인지 알 수 있다.**
- 번호가 붙어 있어서 **같은 워크플로우의 실행 건(예: 청구 건)을 서로 구분할 수 있다.**

> `actor`는 3.3, 4.2 워크플로우 표의 "수행 주체"와 대응한다. 화면에서 **AI가 한 일과 사람이 한 일을 구분**하는 기준이 된다.

| 표의 수행 주체 | `actor` |
|-------------|---------|
| 도구 | `tool` |
| Agent | `agent` (LLM을 한 번만 호출하는 스텝도 포함, 6.3) |
| 프로그램 | `program` |
| 고객/담당자, 담당자, 심사자 | `human` |

#### 실행 규칙 — 스텝은 상위 워크플로우를 통해서만 실행

- 스텝은 **단독으로 실행할 수 없다.** 반드시 상위 워크플로우가 실행할 때만 동작한다.
- 스텝을 실행할 때 **스텝의 `workflow` 값이 현재 실행 중인 워크플로우의 코드와 같은지 확인**하고, 다르면 실행을 거부한다.
- 이 규칙으로 모든 스텝 실행이 어느 워크플로우의 어느 실행에 속하는지 항상 알 수 있다. trace 로그에 워크플로우 ID를 남길 수 있는 근거가 된다.

#### 사람 스텝 — 멈춤과 재개

Streamlit은 화면을 조작할 때마다 스크립트를 처음부터 다시 실행한다. 그래서 사람 입력을 기다리는 동안 워크플로우를 메모리에 둘 수 없다. **스텝마다 상태를 SQLite에 저장하고, 사람 스텝에서 멈췄다가 다음 스텝부터 이어서 실행**한다.

**실행 상태 테이블 (`workflow_runs`)**

| 컬럼 | 설명 |
|-----|------|
| `workflow_id` | PK, 워크플로우 ID |
| `workflow_code` | 워크플로우 코드 |
| `status` | 실행 중 / 검토 대기 / 완료 / 반려 / 실패 |
| `current_step` | 마지막으로 실행했거나 대기 중인 스텝 ID |
| `ctx` | 컨텍스트 전체 (JSON) |
| `updated_at` | 마지막 갱신 시각 |

**동작 방식**

| 상황 | 처리 |
|-----|------|
| 스텝 종료 | ctx와 `current_step`을 저장한다 |
| 사람 스텝(`actor: human`) 도달 | `status`를 "검토 대기"로 저장하고 **실행을 끝낸다** (워크플로우는 "검토 대기"를 반환) |
| Agent 에스컬레이션 | 같은 방식으로 다음 사람 스텝에서 "검토 대기"로 멈춘다 |
| 사람 승인 | 저장된 ctx를 불러와 사람의 입력(승인 여부, 의견)을 넣고 **사람 스텝의 다음 스텝부터 재개**한다 |
| 사람 반려 | `status`를 "반려"로 바꾸고 종료한다. 심사자 의견은 Score에 남긴다 (7.3) |
| 오류 | `status`를 "실패"로 저장한다. 마지막으로 성공한 스텝까지의 ctx는 남아 있다 |

- 검토 화면은 `status`가 "검토 대기"인 실행 건을 목록으로 보여준다.
- ctx는 JSON으로 저장할 수 있는 값만 담는다. 이미지·PDF는 파일 경로만 담는다.

### Agent trace 로그

Agent 실행 기록은 `workflow_id` + `step_id`를 키로 남긴다. 상세 설계는 **7장 Trace 설계**를 따른다.

### 흐름 시각화 화면 (후반 선택 과제)

시간이 남으면 워크플로우 흐름을 보여주는 화면을 추가한다.

| 단계 | 내용 | 시점 |
|----|------|-----|
| 1 | 스텝에 `@step` 어노테이션 부착, 워크플로우는 일반 코드로 작성 | 개발 시작부터 |
| 2 | 워크플로우를 선언형(스텝 목록 + 연결 + 분기 조건)으로 전환 | 시간이 남을 때 |
| 3 | 선언형 정의를 다이어그램으로 그려 Streamlit 화면에 표시 | 시간이 남을 때 |
| 4 | trace 기록(7장)과 결합해 진행 중 스텝·에스컬레이션 지점 강조 | 시간이 남을 때 |

화면에서 보여줄 것:

- 스텝 순서와 분기 (예: 흐름 2의 "AI 판단 필요 여부" 분기)
- 수행 주체별 색 구분 (도구 / Agent / 프로그램 / 사람)
- 사람이 검토·승인하는 지점 강조 → **"수행자 → 검토·승인자" 역할 전환**을 시각적으로 보여준다

## 6. Agent 설계

### 6.1 원칙

- LangChain 등 Agent 프레임워크를 쓰지 않고 **직접 구현**한다.
- LLM은 **OpenAI GPT API**를 사용한다. 함수 호출(function calling)과 구조화 출력(Structured Outputs)을 활용한다.
- 직접 구현하는 기능은 **툴콜링, 스킬, Agent loop** 3가지다.
- Agent는 항상 **스텝 안에서만 실행**된다. 그래서 Agent의 모든 동작은 `workflow_id` + `step_id`로 추적된다.

### 6.2 구성 요소

| 구성 요소 | 역할 |
|---------|------|
| LLM Client | OpenAI API 호출을 감싼다. 호출마다 trace에 Generation을 자동으로 남긴다 |
| Agent Loop | LLM 호출 → 툴 실행 → 결과 전달을 종료 조건까지 반복한다 |
| Tool Registry | 툴 정의(이름, 설명, 파라미터 스키마)와 실행 함수를 등록·조회한다 |
| Skill Loader | 스킬 폴더를 읽어 스킬 목록과 상세 지침을 제공한다 |
| Tracer | 현재 워크플로우·스텝 정보를 들고 다니며 trace를 기록한다 (7장) |

### 6.3 Agent 정의

Agent는 아래 항목으로 정의한다.

| 항목 | 설명 |
|-----|------|
| `name` | Agent 이름 |
| `model` | 사용할 GPT 모델 (설정으로 변경 가능) |
| `system_prompt` | 역할과 원칙 (추측 금지, 에스컬레이션 원칙 포함) |
| `tools` | 사용할 수 있는 툴 목록 |
| `skills` | 사용할 수 있는 스킬 목록 |
| `output_schema` | 최종 출력 JSON 스키마 (예: 판단 항목의 `outputSchema`) |
| `max_iterations` | Agent loop 최대 반복 횟수 |
| `planning` | 계획 수립·순차 처리 사용 여부 (켜면 `update_plan` 툴이 추가된다, 6.4) |

> LLM을 한 번만 호출하는 작업(예: 이미지 분류·태깅, 청구정보 생성)도 **툴 없이 `max_iterations` 1인 Agent**로 만든다. 구현과 trace 기록 방식이 Agent loop 하나로 통일된다.

### 6.4 Agent Loop

```
시작: 시스템 프롬프트 + 사용 가능한 스킬 목록 + 입력으로 대화 구성
  │
  ▼
LLM 호출 (툴 목록 전달) ◀──────────────────────────────┐
  │                                                  │
  ├─ 응답에 tool call 있음 ─▶ 툴 실행 ─▶ 결과를 대화에 추가 ─┤
  │                                                  │
  └─ tool call 없음 (최종 응답)                          │
       │                                             │
       ├─ [planning 켜짐] 계획에 남은 항목 있음             │
       │      ─▶ "남은 항목: …, 계속 진행" 메시지 추가 ──────┘
       │
       └─ 남은 항목 없음 ─▶ output_schema 검증 ─▶ 종료
```

- Agent loop는 **툴을 호출할 때**와 **계획에 남은 항목이 있을 때** 다음 턴으로 넘어간다.

| 종료 조건 | 처리 |
|---------|------|
| 최종 응답 + 스키마 검증 통과 | 정상 종료, 결과 반환 |
| 최종 응답인데 계획에 남은 항목 있음 (planning) | 남은 항목을 알려주고 loop를 계속한다. 3회 연속 진행이 없으면 에스컬레이션 |
| 스키마 검증 실패 | 오류 내용을 알려주고 1회 재시도, 다시 실패하면 에스컬레이션 |
| `escalate` 툴 호출 | 에스컬레이션으로 종료 (사람 검토 필요). 흐름 1 변환처럼 끝까지 진행해야 하는 Agent는 이 툴 대신 출력의 미정의 항목 목록을 쓴다 (3.4) |
| `max_iterations` 초과 | 에스컬레이션으로 종료 |
| API 오류 | 정해진 횟수만큼 재시도 후 실패 처리 |

#### 계획 수립과 순차 처리 (planning)

여러 단계로 나눠야 하는 작업(예: 흐름 1의 조항별 스키마 변환, 계산 Tool 생성)은 Agent가 **먼저 계획을 세우고 항목을 하나씩 처리**한다. Agent 정의의 `planning`을 켠 Agent만 사용한다.

| 순서 | 동작 |
|-----|------|
| 1 | 시스템 프롬프트에 "먼저 `update_plan`으로 계획을 세우라"는 지침을 넣는다 |
| 2 | Agent가 `update_plan`으로 할 일 목록을 만든다 |
| 3 | 항목을 하나씩 진행 중으로 바꾸고, 다른 툴로 처리한 뒤 완료로 바꾼다 |
| 4 | 처리하면서 필요하면 항목을 추가·수정·삭제한다 (계획 수정) |
| 5 | 모든 항목이 완료 또는 건너뜀이 되면 최종 응답을 낸다 |

**`update_plan` 툴**

| 항목 | 내용 |
|-----|------|
| 입력 | 계획 전체 목록 (호출할 때마다 목록 전체를 새로 보낸다) |
| 항목 구성 | 내용, 상태 (`대기` / `진행 중` / `완료` / `건너뜀`), 건너뜀 사유 |
| 규칙 | `진행 중`은 한 번에 1개만. `건너뜀`은 사유 필수 |
| 저장 | Agent loop가 현재 계획을 들고 있고, 바뀔 때마다 trace에 남긴다 (7장) |

- 계획에 남은 항목이 있는데 Agent가 최종 응답을 내면, loop가 남은 항목을 알려주고 계속 진행시킨다.
- planning을 켠 Agent는 반복 횟수가 많아지므로 `max_iterations`를 넉넉히 잡는다.

### 6.5 툴콜링

| 항목 | 내용 |
|-----|------|
| 툴 정의 | 이름, 설명, 파라미터 JSON 스키마, 실행 함수 |
| 전달 방식 | Agent에 허용된 툴만 OpenAI 함수 호출 형식으로 LLM에 전달 |
| 실행 | LLM이 준 인자를 스키마로 검증한 뒤 실행하고, 결과를 JSON으로 대화에 추가 |
| 여러 툴 동시 호출 | 한 응답에 tool call이 여러 개면 모두 실행한 뒤 결과를 한꺼번에 전달 |
| 오류 처리 | 툴 오류는 Agent를 멈추지 않고 오류 내용을 툴 결과로 LLM에 전달해 다른 방법을 찾게 한다 |

모든 Agent가 공통으로 가지는 툴:

| 툴 | 역할 |
|---|------|
| `load_skill` | 스킬의 상세 지침을 불러온다 (6.6) |
| `escalate` | 판단할 수 없으면 사유와 함께 사람에게 넘기고 Agent를 종료한다 (종료형). 흐름 1 변환의 미정의 항목은 수집형으로 처리한다 (3.4) |
| `update_plan` | 계획을 세우고 항목 상태를 갱신한다. **`planning`을 켠 Agent에만** 추가된다 (6.4) |

### 6.6 스킬

스킬은 **특정 작업을 하는 방법을 담은 지침 묶음**이다. 예: "보험금계산 프로그램 생성" 스킬.

| 항목 | 내용 |
|-----|------|
| 위치 | `src/skills/<스킬명>/` 폴더 1개 = 스킬 1개 |
| 구성 | 스킬 설명 파일(이름, 한 줄 설명, 상세 지침) + 필요한 참고 자료·템플릿 |
| 노출 방식 | 시스템 프롬프트에는 **이름과 한 줄 설명만** 넣는다 |
| 사용 방식 | Agent가 필요하다고 판단하면 `load_skill` 툴로 상세 지침을 불러온다 |

- 처음부터 모든 지침을 넣지 않고 필요할 때만 불러오므로 프롬프트가 짧아진다.
- 스킬을 불러온 기록도 trace에 남아서, Agent가 어떤 지침을 보고 작업했는지 확인할 수 있다.

## 7. Trace 설계 (Langfuse 참고)

### 7.1 개념 매핑

Langfuse의 Trace / Observation / Score 구조를 따른다.

| Langfuse 개념 | 이 프로젝트에서 | 식별 |
|-------------|--------------|------|
| Trace | 워크플로우 실행 1건 | `workflow_id` (예: `claim_review_000001`) |
| Span | 스텝 실행, Agent 실행, 툴 실행 | `step_id` + `observation_id` |
| Generation | LLM 호출 1회 (모델, 프롬프트, 응답, 토큰, 비용) | `observation_id` |
| Event | 순간 기록 (에스컬레이션, 스키마 검증 실패, 스킬 로드, 계획 갱신) | `observation_id` |
| Score | 사람의 평가 (심사자 승인/반려, 수정 여부) | `workflow_id` + `step_id` + `observation_id` |

> Score로 **AI 결과에 대한 사람의 최종 판단**을 남긴다. 담당자가 "검토·승인자"로 일한 기록이 된다.

### 7.2 계층 구조 예시

```
Trace  claim_review_000001  보험금 청구 심사 지원
├─ Span  [step] classify_images  이미지 분류 및 태깅
│   └─ Generation  이미지 분류 LLM 호출
├─ Span  [step] identify_judgments  판단 필요 항목 식별
├─ Span  [step] judge_items  AI 판단 항목 처리
│   └─ Span  [agent] 판단 Agent
│       ├─ Generation  LLM 호출 #1  → tool call: load_skill
│       ├─ Span  [tool] load_skill
│       ├─ Generation  LLM 호출 #2  → tool call: 서류 조회
│       ├─ Span  [tool] 서류 조회
│       ├─ Generation  LLM 호출 #3  → 최종 응답
│       └─ Event  출력 스키마 검증 통과
├─ Span  [step] calculate_claim  보험금 계산
└─ Span  [step] review_approval  심사자 검토·승인
    └─ Score  심사자 승인
```

- **모든 스텝을 Span으로 기록**한다. Agent가 없는 스텝도 시작·종료·입출력을 남겨서 흐름 전체를 따라갈 수 있게 한다.
- Agent 스텝은 스텝 Span 아래에 Agent loop 안의 LLM 호출과 툴 실행을 순서대로 남긴다.
- planning을 켠 Agent는 `update_plan`이 호출될 때마다 **계획 갱신 Event**(`kind: plan`)에 그 시점의 계획 전체를 남긴다. 계획이 어떻게 세워지고 바뀌었는지 따라갈 수 있다.

### 7.3 데이터 모델 (SQLite)

모든 기록에 **`workflow_id`와 `step_id`**가 들어간다.

#### traces — 워크플로우 실행

| 컬럼 | 설명 |
|-----|------|
| `workflow_id` | PK, 실행 건마다 유일 |
| `workflow_code` / `workflow_name` | 워크플로우 코드·이름 |
| `status` | `workflow_runs.status`와 같은 값 (실행 중 / 검토 대기 / 완료 / 반려 / 실패) |
| `input` / `output` | 워크플로우 입력·최종 결과 |
| `started_at` / `ended_at` | 시작·종료 시각 |
| `total_tokens` / `total_cost` | 전체 토큰·비용 합계 |

#### observations — 스텝·Agent·LLM·툴 기록

| 컬럼 | 설명 |
|-----|------|
| `observation_id` | PK |
| `workflow_id` | 소속 워크플로우 실행 |
| `step_id` | 소속 스텝 |
| `parent_id` | 상위 기록 (트리 구성용) |
| `type` | `SPAN` / `GENERATION` / `EVENT` |
| `kind` | `step` / `agent` / `tool` / `llm` / `skill` / `plan` / `escalation` |
| `name` | 표시 이름 (스텝명, 툴 이름 등) |
| `level` | `DEBUG` / `DEFAULT` / `WARNING` / `ERROR` |
| `status_message` | 오류·경고 메시지 |
| `input` / `output` | 입력·출력 (JSON) |
| `started_at` / `ended_at` | 시작·종료 시각 (소요 시간 계산) |
| `model` / `model_params` | Generation만: 모델명, 파라미터 |
| `prompt_tokens` / `completion_tokens` / `cost` | Generation만: 토큰 사용량, 비용 |

#### scores — 사람의 평가

| 컬럼 | 설명 |
|-----|------|
| `score_id` | PK |
| `workflow_id` / `step_id` | 평가 대상 워크플로우 실행·스텝 |
| `observation_id` | 평가 대상 Agent 실행 기록 (스텝 전체를 평가하면 비움) |
| `name` | 평가 항목 (예: 심사자 승인) |
| `value` | 승인 / 반려 / 수정 후 승인 |
| `comment` | 심사자 의견 |
| `created_by` / `created_at` | 평가자·시각 |

> 판단 항목이 여러 개면 **판단 항목마다 Agent를 따로 실행**한다. 그래서 `observation_id`로 판단 항목별 승인·반려를 구분할 수 있다.

### 7.4 기록 방식

- 워크플로우가 시작되면 Trace를 만들고, 스텝이 실행될 때마다 스텝 Span을 연다.
- Tracer가 현재 `workflow_id`와 `step_id`를 들고 있어서, 그 안의 LLM 호출·툴 실행은 **자동으로 같은 키로 기록**된다. 개발자가 로그 코드를 따로 쓰지 않는다.
- 이미지·PDF 같은 큰 데이터는 내용 대신 **파일 경로**만 기록한다.

## 8. 팀 개발 규칙

3명이 Codex와 Claude Code로 동시에 개발한다. 서로의 작업에 영향을 주지 않도록 **영역 소유권, 인터페이스 고정, 자동 검사** 3가지로 규칙을 강하게 적용한다.

### 8.1 영역 분담 (소유권)

| 담당 | 영역 | 소유 폴더 |
|-----|------|---------|
| 팀원 A | 흐름 1 — 약관 구조화 | `workflow/policy_structuring.py`, `workflow/steps/policy_structuring/`, 흐름 1용 스킬 (`skills/` 아래 해당 폴더) |
| 팀원 B | 흐름 2 — 청구 심사 | `workflow/claim_review.py`, `workflow/steps/claim_review/`, 흐름 2용 스킬 |
| 팀원 C | 공통 기반 | `agent/`, `trace/`, `backend/`, 공통 `schema/`, 앱 뼈대 `app/main.py`, trace 조회 화면 |

- **자기 소유 폴더만 수정한다.** 다른 사람 폴더를 고쳐야 하면 소유자에게 요청한다.
- 화면(`app/views/`)은 **흐름별로 파일을 나눈다.** 각자 자기 화면 파일만 수정한다.
- `schema/`도 흐름별 파일로 나눈다. 여러 흐름이 같이 쓰는 모델만 공통 파일에 두고, 공통 파일은 팀원 C가 관리한다.

### 8.2 공통 인터페이스 먼저 고정

개발을 시작하면 **첫 1시간 안에 팀원 C가 아래 인터페이스를 먼저 만들고 고정**한다. A와 B는 이 인터페이스만 보고 개발한다.

| 인터페이스 | 내용 |
|----------|------|
| 컨텍스트(ctx) | 스텝 사이에 주고받는 공통 데이터 구조 |
| 실행 상태 저장·재개 | `workflow_runs` 테이블, "검토 대기" 반환 방식, 재개 시작 스텝 (5장 사람 스텝) |
| `@workflow` / `@step` | 어노테이션 항목 (5장) |
| Agent 정의 | 6.3의 항목 |
| 툴 정의 | 이름, 설명, 파라미터 스키마, 실행 함수 (6.5) |
| Tracer | 기록 시작·종료 방법 (7장) |
| DB 접근 | 연결 방법, 테이블 생성 방법 |

- 고정한 뒤 바꿔야 하면 **팀 전체에 먼저 알리고 합의한 뒤** 팀원 C가 바꾼다.
- 공통 기반이 완성되기 전에는 A와 B가 **가짜 구현(mock)**으로 개발해서 기다리지 않는다. 예: LLM 대신 정해진 응답을 돌려주는 가짜 Client.

### 8.3 공유 파일 규칙

여러 명이 함께 건드리는 파일은 충돌이 가장 많이 나는 곳이라 관리자를 1명으로 정한다.

| 파일 | 관리자 | 규칙 |
|-----|-------|------|
| 의존성 목록 (`requirements.txt` 등) | 팀원 C | 라이브러리 추가는 요청하고, 버전을 고정한다 |
| 앱 진입점 (`app/main.py`) | 팀원 C | 화면 등록 한 줄만 추가한다 |
| DB 테이블 | 각자 | 흐름별 테이블은 이름 앞에 흐름 코드를 붙인다. 공통 테이블(trace 등)은 팀원 C가 관리한다 |
| 설정·비밀값 | 각자 | `.env`는 커밋하지 않는다. 필요한 키 목록은 `.env.example`에 적는다 |
| SQLite DB 파일 | — | 커밋하지 않는다. 각자 로컬에서 생성한다 |
| 생성된 계산 Tool | — | 커밋하지 않는다 (3.5) |

### 8.4 Git 규칙

#### 브랜치 구조

| 브랜치 | 용도 | 만드는 위치 |
|-------|------|----------|
| `main` | `README.md`만 둔다. 개발에 사용하지 않는다 | — |
| `product` | **검증이 끝나 시연에 쓸 수 있는 코드**만 둔다 | `main`에서 생성 |
| `develop` | 각자 작업을 합쳐서 **함께 테스트**하는 브랜치 | `product`에서 생성 |
| 개인 작업 브랜치 | 기능 1개 개발 | `product`에서 생성 |

```
main ── README.md만
  └─ product ──────────●──────────────●────────▶  (검증된 것만, 시연용)
        ├─ develop ──●──●──●──●──●──●──●──────▶  (통합 테스트용)
        ├─ feat/claim-이미지분류 ─┬─▶ develop (테스트)
        │                       └─▶ product (검증 후)
        └─ feat/common-tracer ──┬─▶ develop
                                └─▶ product
```

#### 작업 흐름

1. `product`에서 개인 브랜치를 만든다.
2. 개발이 끝나면 개인 브랜치를 `develop`에 머지하고, 다른 사람 작업과 합친 상태에서 테스트한다.
3. 테스트를 통과하면 **같은 개인 브랜치**를 `product`에 머지한다 (PR).
4. `product`에 머지한 직후 `product`에서 실행 확인을 한 번 더 한다.
5. 머지가 끝난 개인 브랜치는 삭제하고, 다음 작업은 `product`에서 새로 브랜치한다.

#### 반드시 지킬 규칙

| 규칙 | 이유 |
|-----|------|
| **`develop` → `product` 머지 금지** | `develop`에는 검증 안 된 작업이 섞여 있다. `product`에는 개인 브랜치만 머지한다 |
| **`develop` → 개인 브랜치 머지 금지** | 개인 브랜치에 검증 안 된 남의 코드가 들어가고, 그 상태로 `product`에 가면 같이 딸려 들어간다 |
| 개인 브랜치 최신화는 `product`에서만 | 남의 작업이 필요하면 그 작업이 `product`에 들어온 뒤 받는다 |
| 공통 기반(팀원 C)은 가장 먼저 `product`에 머지 | A, B의 브랜치가 `product`에서 시작하므로, 공통 인터페이스가 `product`에 있어야 쓸 수 있다 |
| `product`에 머지할 때 squash 하지 않음 | squash 하면 `develop`과 `product`의 기록이 달라져 이후 머지에서 충돌이 난다 |
| `develop` 충돌 해결은 개인 브랜치에 넣지 않음 | 충돌은 `develop` 머지 커밋 안에서만 해결한다 |

#### 기타 규칙

| 규칙 | 내용 |
|-----|------|
| 기본 브랜치 | GitHub 기본 브랜치를 `product`로 설정한다 (`main`은 README뿐이라 clone 시 빈 화면이 된다) |
| 브랜치 보호 | `product`: 직접 push 금지, PR로만 머지. `develop`: 직접 머지 허용. GitHub Free 플랜 private 저장소는 브랜치 보호를 쓸 수 없으므로 **push 전 검사로 막는다** (8.5) |
| 브랜치 이름 | `feat/<영역>-<내용>` (영역: `policy` / `claim` / `common`) |
| 작게 자주 | 기능 단위로 작게 나눠 자주 머지한다 (1시간 이상 묵히지 않는다) |
| `develop` 초기화 | `develop`이 너무 꼬이면 팀 합의 후 `product` 기준으로 다시 만든다 (`develop`에는 버릴 수 있는 것만 있다) |
| 시연 전 태그 | 시연에 쓸 `product` 시점에 태그를 붙여(예: `demo-1`) 문제가 생기면 바로 돌아간다 |
| 금지 | force push 금지 (`develop` 초기화 제외). 다른 사람이 작성한 커밋은 되돌리지 않는다 |
| 커밋 메시지 | `[영역] 내용` 형식 (예: `[claim] 이미지 분류 스텝 추가`) |

### 8.5 AI 코딩 도구 규칙 (Codex, Claude Code)

AI 도구는 지시가 없으면 관련 없는 파일까지 고치는 경향이 있다. 그래서 **지침 파일로 규칙을 알려주고, 자동 검사로 막는다.**

#### 지침 파일

| 도구 | 읽는 파일 |
|-----|---------|
| Codex | `AGENTS.md` |
| Claude Code | `CLAUDE.md` |

- 규칙은 **`AGENTS.md` 한 곳에만** 쓴다. `CLAUDE.md`는 `AGENTS.md`를 불러오기만 해서 두 도구가 같은 규칙을 따르게 한다.
- 프로젝트 루트에는 공통 규칙을, 각 영역 폴더에는 그 영역만의 규칙을 둔다. 두 도구 모두 작업 중인 폴더의 지침 파일을 추가로 읽는다.

#### 지침 파일에 넣을 규칙

1. 이 작업자의 담당 영역 폴더 밖의 파일은 수정하지 않는다. 필요하면 수정하지 말고 무엇이 필요한지 보고한다.
2. 공통 인터페이스(8.2)는 바꾸지 않는다.
3. 라이브러리를 새로 추가하지 않는다.
4. 요청받지 않은 리팩터링, 파일 전체 포맷 변경, 파일 이름 변경을 하지 않는다.
5. 5장 workflow 구성 규칙과 스텝 작성 규칙을 따른다.
6. Agent는 LangChain 없이 6장 설계대로 구현한다.
7. 커밋하기 전에 실행 확인을 한다.

#### 자동 검사 (규칙을 어기면 막기)

지침만으로는 AI가 실수할 수 있으므로 **도구와 상관없이 Git 단계에서 막는다.**

| 장치 | 내용 |
|-----|------|
| 소유권 목록 파일 | 폴더별 소유자를 적은 파일 (GitHub `CODEOWNERS` 형식) |
| 커밋 전 검사 (pre-commit hook) | 커밋에 소유하지 않은 폴더의 파일이 있으면 커밋을 거부한다. **`develop` 브랜치의 커밋은 검사하지 않는다** (여러 사람 작업을 합치고 충돌을 해결하는 곳이라서. `product` 머지는 PR로 따로 검토한다) |
| `product` 보호 (push 전 검사, pre-push hook) | 각자 PC에서 `product`로 직접 push하면 거부한다. GitHub Free 플랜 private 저장소는 브랜치 보호와 CODEOWNERS 승인 강제를 쓸 수 없어서 로컬 검사로 대신한다. 다른 사람 영역이 바뀐 PR은 소유자가 직접 확인하고 머지한다 (팀 약속) |
| Claude Code 추가 설정 | 권한 설정에서 담당 영역 밖 파일 수정을 금지한다 (개인 설정) |

### 8.6 시작 순서

| 순서 | 할 일 | 담당 |
|-----|------|------|
| 1 | 저장소 생성, `main`(README) → `product` → `develop` 브랜치 생성, 폴더 구조, `AGENTS.md`/`CLAUDE.md`, 소유권 목록, 커밋 전 검사 설정 | 팀원 C (A, B는 그동안 자기 흐름의 스텝 설계 확인) |
| 2 | 공통 인터페이스 고정 (8.2) 후 **가장 먼저 `product`에 머지** | 팀원 C |
| 3 | 각자 `product`에서 브랜치해서 개발 시작 (공통 기반이 안 됐으면 가짜 구현 사용) | 전원 |
| 4 | 정해진 시간마다 `develop`에 합쳐 테스트하고, 통과한 브랜치만 `product`에 머지 | 전원 |
